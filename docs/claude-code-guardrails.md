# Claude Code guardrails

Mechanics of the Claude Code hooks and project agent. Why they are shaped this way: [`docs/agent-behavior-design.md`](./agent-behavior-design.md).

**Start every session at the primary root, or a workspace's root.** The settings, hooks and agent load only from a root's `.claude/`, so a session started inside `packages/*` runs with none of them. Each package's `CLAUDE.md` says so; restart at a root.

## The hooks and the project agent

`.claude/settings.json` registers fifteen Node hooks in `.claude/hooks/`, TypeScript that `node` runs by stripping types (erasable syntax only, `.ts` imports, nothing from `packages/`), plus one project agent. Every hook fails open (bad input allows the call) unless noted. Six gate a call: `bashReadGuard.ts`, `tierGate.ts`, `gmailGate.ts`, `branchGuard.ts`, `primaryEditGuard.ts` and `readFirstGate.ts`. `branchRecord.ts` records what `branchGuard.ts` reads, `sessionEndRelease.ts` ends a session's supervision and releases its leases, and `sessionIdContext.ts` records an interactive session in its issue's facts file. The other six add feedback or a reminder. A sixteenth, `stepPermission.ts`, is registered only in a runner step's own settings. Each command roots its hook file at `BYRO_GATE_ROOT`, falling back to `$CLAUDE_PROJECT_DIR`, so an interactive session, which leaves it unset, runs its own root's hooks; what setting it does: [hook dedupe and the gate root](./claude-code-behaviour.md#hook-dedupe-and-the-gate-root).

**A runner step runs the primary's gate through the gate root.** `runner/src/ClaudeAgentStep.ts` launches each step with `BYRO_GATE_ROOT` set to the primary checkout, and passes the primary's `.claude/settings.json` in `--settings`, with the primary's `stepPermission.ts` added as a PermissionRequest hook on `Edit|Write|Bash|Read`, injected from `scripts/runner/runnerConfig.ts`. A step writes anywhere in its workspace, `$TMPDIR` or `/tmp` but `.git`, protected paths included, since git or throwing the workspace away undoes the write, and a workspace's `.git` points into the primary's git folder. `.githooks/` is the commit gate, and Claude Code doesn't protect it (2.1.312, #446), so a step's edit there changes the commit check for its own workspace's commits, which review sees and git undoes. Project settings stay loaded, so the workspace's skills and agents still load, and each hook runs once, from the primary's file: a step's edit to a hook file or to its workspace's `settings.json` can't remove a primary gate, and a gate change a ticket makes reaches steps only once it lands on master. What's left: a step can add a hook or a permission rule, in `settings.json` or the gitignored `settings.local.json`, that applies to the later steps on its own ticket.

- **`bashReadGuard.ts`** (PreToolUse, Bash) denies a Bash read of `columnConfigs.ts`, unless it is a grep or a `sed -n` range of at most 150 lines. It also denies a whole-file dump (`cat`, unbounded `head`/`tail`, `sed` without `-n`, `sed -n '1,$p'`) of a repo file over 150 lines. The deny message names the alternative. Piped input, small files, anything under a `.probe/`, `dist/`, `coverage/` or `node_modules/` folder at any depth, and anything outside the repo are not guarded. The `columnConfigs.ts` it guards is every package's, the primary's or a workspace's, found through the `generatedDir` in each `sheets.config.json` (`lib/sheetsConfigs.ts`). Its classifier, `lib/tiers/bashReads.ts`, is tested beside it and shared with `readCountNudge.ts`.
- **`tierGate.ts`** (PreToolUse, Bash and the gworkspace write and create tools; PostToolUse, Bash) applies [the tier rows](./targets-and-gates.md#which-tier-an-action-is-in), allowing what they make free or give a standing yes, and asking for the tier-3 rows other than Gmail's, which is `gmailGate.ts`'s; inline code it refuses, naming the free way through. PostToolUse records each chore dry run, and an `app:chore <name> -- --send` with none is refused. A Supervisor's `gh` writes are as free as any interactive session's: the gate no longer reads the supervision record, since its ask was a rubber stamp on replies the developer had already settled in chat, and a misread reply costs run time that a further comment or edit undoes (#450). A gworkspace write's owner comes from Drive's `owners` field, read with the gworkspace server's stored token for the agent account (`lib/tiers/driveOwners.ts`) and cached per session. In a runner step, which `runner/src/ClaudeAgentStep.ts` marks with `BYRO_RUNNER_STEP`, every ask becomes [the tiers' runner-step refusal](./targets-and-gates.md#the-tiers); the step gets every free and tier-1 action the gate allows, and nothing else. A plain `git merge` is among them, looser than before, when it fell to tier 3 and the merge-master step could never merge `master` into a ticket's branch on a wrap-up conflict (#466); `primaryEditGuard.ts` keeps it out of a primary checkout. Other git verbs that change anything (`checkout`, `reset`, `stash`, `rebase`, a `branch` delete or force, a `restore` outside its own workspace) stay denied. A call the gate doesn't classify is denied too, with the `blockerInstead` text, `gh` and live aliases included: the gate, not Claude Code's allow rules, gives a step its `gh issue edit` and `comment` and its targets' live aliases, and denies its `gh issue close` (#445); a step reads issues through `npm run issue:read`, never `gh` ([ADR 0007](./adr/0007-keep-untrusted-text-out-of-instructions-and-defer-containment.md)). The path-checked file commands and scratch `node` follow [their tier rows](./targets-and-gates.md#which-tier-an-action-is-in), which give why `node` runs only scratch helpers; the write rule is `lib/tiers/stepWrites.ts`, and it refuses `claude-guardrails/` in `$TMPDIR` or `/tmp` so a write can't forge a chore's dry-run record. A gworkspace write is denied unless its file is among the ticket's targets, which `BYRO_STEP_TARGETS` carries ([ticket targets](./targets-and-gates.md#ticket-targets)). The one push it allows is `npm run wrap-up`'s, and wrap-up scans the lines each master adds over its remote for token shapes before pushing; a hit fails at `secret-scan`, naming file and line, and nothing is pushed ([`runner/src/WrapUp.ts`](../runner/src/WrapUp.ts)). The decisions are `lib/tiers/tiers.ts` and `lib/tiers/driveTiers.ts`, tested beside them; its file-system lookups are `lib/gateLookups.ts`, shared with `stepPermission.ts`.
- **`stepPermission.ts`** (PermissionRequest, Edit, Write, Bash and Read; registered only in a runner step's `--settings`) answers the prompt Claude Code raises for a protected path such as `.claude/`, `.vscode/` or `.mcp.json` even after the tier gate allows. It allows an Edit or Write whose path passes the step write rule (inside the workspace, `$TMPDIR` or `/tmp`, never `.git` at any depth, symlinks resolved and a dangling one refused), a Bash call only when `tierGate.ts`'s decision allows it, so a Bash write and an Edit to one path get one answer, and any Read. Everything else, and every call outside a runner step, gets no decision, so a step records a `denied-tool` blocker. The decision is `lib/tiers/stepPermission.ts`, tested beside it.
- **`gmailGate.ts`** (PreToolUse, the four gmail filter, label and message-label tools) is the second half of an `/inbox` Sign-off. It allows a call when one `signed-off` Proposal in `inbox/proposals.md` of the session's own `packages/personal` clone covers it, and asks otherwise. A filter is covered when every criterion sits in the Proposal's query and every label it adds or removes sits in the action's `add` or `remove` clause. A bulk or unsubscribe change is covered the same way, and so is a new label whose name the `add` clause holds. A label named there that was created on apply counts by the id `changes.md` records for it. It denies adding `SPAM`, asks for any filter action other than adding and removing labels, and fails closed: unreadable data asks. Sending and drafting stay denied in settings. The decision is `lib/tiers/gmailGate.ts` and the data lookup `lib/tiers/inboxData.ts`, each tested beside it.
- **`branchGuard.ts`** (PreToolUse, Bash) keeps a primary checkout (the root or a clone under `packages/`) on its branch. Its `mode` is strict: it denies every branch move (`git checkout <branch|sha>`, `checkout -b`, `switch`, `switch -c`) in a primary checkout. The interim form it replaced, still in `lib/branchGuard.ts`, left branch moves alone and denied only a `git commit` once HEAD's commit or branch changed since this session recorded it. File restores (`checkout -- <path>`, `checkout <ref> [--] <path>`, or a lone operand naming an existing path) always pass, `git -C` and `cd … &&` resolve the checkout acted on, and a target under `.claude/worktrees/`, where issue and session workspaces live beside Claude Code's own worktrees, is never denied. Subshells (`(cd x && …)`), `pushd`, `--git-dir` and `--work-tree` are not resolved: the guard catches accidents, not evasion. After its own HEAD-moving git command, a session's record is re-recorded before its next decision. Each deny names the way through: the issue workspace, or a fresh session once the other one is done. The decision is `lib/branchGuard.ts`, tested beside it; the I/O is `lib/branchRecords.ts`.
- **`primaryEditGuard.ts`** (PreToolUse, Edit/Write/NotebookEdit and Bash) keeps a session's edits, commits and merges out of a primary checkout, where runs land. A file tool's path resolves through symlinks (a new file through its nearest existing folder) to the deepest primary checkout holding it, so a package clone is judged before the root that ignores `packages/*`. It is denied unless that checkout gitignores it: `.runner/`, `.probe/` and `node_modules` pass, as do `.claude/worktrees/`, which holds every issue and session workspace, and any path outside every checkout. On Bash it denies a `git commit` or `git merge` resolving to a primary checkout, resolving `git -C` and `cd … &&` as `branchGuard.ts` does. The merge denial is stricter than before, when only the tier gate's ask stood between a session at the primary root and a merge into master in place (#466). Bash writes such as `sed -i`, `rm` and redirects are not caught here: `tierGate.ts`'s write rule checks them against the session's own root and `$TMPDIR`, which keeps a runner step's in its workspace but lets a session started at the primary root write there. The guard catches accidents, not evasion. It is no tier gate, and a runner step meets it unchanged. The deny names `/start-issue <repo> <n>`, which moves the session into an issue workspace, then `npm run issue:start -- <repo> <n>` and `npm run issue:start -- --session <slug>`, and says to continue at the printed path. The decision is `lib/primaryEditGuard.ts`, tested beside it.
- **`branchRecord.ts`** (SessionStart, SessionEnd) records each primary checkout's branch and HEAD at the start of a session started at the primary root, keeping a live record across a compact, and marks it ended at the end, so a resumed session starts a fresh record. A record with no end, written under a day ago, is live.
- **`sessionEndRelease.ts`** (SessionEnd) releases what a session end lets go of, for the session's claude process, the nearest `claude` ancestor of the hook (`scripts/runner/claudeAncestor.ts`, the same walk `npm run issue:start` uses to take a lease). On every end, `/clear` and `/resume` included, it ends the session's supervision record, the runner's `SupervisionRecords` file under `.runner/supervision/<pid>.json` naming the spec whose run this claude supervises and how many of its event lines it has explained, written by `npm run runner -- supervise <owner/repo> <n>` ([`runner/src/SupervisionRecords.ts`](../runner/src/SupervisionRecords.ts)): the record keeps its offset and the end's reason but no longer makes the session the spec's Supervisor, so the spec's watch exits with no output and a conversation after `/clear` hears no run's events until `/runner` rejoins from the last explained event. Only an end of the claude process itself also releases every live workspace lease that process holds, so an interactive session's workspace is never released by hand; a `/clear` or `/resume` end keeps them, since the same process carries on. A session holding no lease or record changes nothing, and a runner step (`BYRO_RUNNER_STEP`) is skipped, since the run holds its lease under its own pid. It reads only the lease files, through the runner's `IssueWorkspaces.leases()` with byro-repo's config (`scripts/runner/runnerConfig.ts`), so no git runs at session end; a checkout needs `npm install` first. The decisions are `lib/sessionEndRelease.ts`, tested beside it.
- **`sessionIdContext.ts`** (SessionStart) puts `session: <id>` in context, for a handoff's `session:` line. When the session's claude (the same ancestor walk as `sessionEndRelease.ts`) holds an issue workspace's lease and `BYRO_RUNNER_STEP` is unset, it also adds `{agent: "implement", sessionId}` under that issue's `sessions` in `.runner/<repo>-<n>.facts.json`, through the runner's `FactsFile.addSession`, with the active `cswap` account and the config folder above the session's transcript, for wrap-up to read ([git-workflow](./agents/git-workflow.md)). A handoff's next session appends; a resumed or compacted session, keeping its id, isn't added twice; no lease, a session workspace's lease or a runner step adds nothing, and an unknown account or config folder skips the record. On a `clear` start whose cwd is inside an issue workspace leased to this claude, it adds one more line: the issue, that `/start-issue <repo> <n>` continues it from its handoff, and that work outside it needs `ExitWorktree` with `keep` first. A hook can't move the session's cwd, so that line is the whole mechanism. On a `clear` or `resume` start whose claude holds a supervision record, ended or not, whose spec's run is running (`SupervisionRecords.runningRecordOf`; never a runner step's), it adds one line naming the run: once `sessionEndRelease.ts` has ended the supervision, that this session supervised it until `/clear` (or `/resume`) and that `/runner <owner/repo> <n>` rejoins from the last explained event; while it still supervises, that `/runner <owner/repo> <n>` carries on from there and `/runner` on another spec switches. With no record, or one whose run has ended, it adds nothing. The decisions are `lib/sessionRecord.ts`, tested beside it. A session that leases its workspace later, through `/start-issue`, is recorded by `npm run issue:start` instead, from `CLAUDE_CODE_SESSION_ID` and `CLAUDE_CONFIG_DIR` (falling back to `~/.claude`), except a Supervisor's session, whose claude holds a supervision record; its decision is `scripts/runner/startedSession.ts`.
- **`sessionPairContext.ts`** (PostToolUse, Bash) adds `This session runs <Family> <effort>.` after a Bash call that starts `npm run issue:start`, for `/start-issue`'s model-fit check, since an agent can't see its own `/effort`. It reads the latest main-loop assistant entry in the session's transcript through the runner's `latestPairOf`, which spells the pair as wrap-up's outcome rows do, and adds nothing when that entry has no `effort` field, which Claude Code doesn't document. The decision is `lib/sessionPairContext.ts`, tested beside it.
- **`generatedEditWarning.ts`** (PreToolUse, Edit/Write) warns, without blocking, before an edit inside any package's `generatedDir`, the primary's or a workspace's, naming that package's `*:gen:configs`: regenerate instead, floor entries included: fix the live tab or the seed ([`docs/generated-data.md`](../packages/framework/docs/generated-data.md)).
- **`agentsCostNudge.ts`** (PreToolUse, Edit/Write) reminds, without blocking, on the first edit to the root `AGENTS.md` in a session, the primary's or a workspace's, once: every byte of that file loads on every turn, so add only what changes behavior on nearly every task ([`prose-style.md`](./prose-style.md#placement), [`prose-files.md`](./agents/prose-files.md#what-an-addition-to-agentsmd-costs)). Nested `AGENTS.md` files draw nothing. The decision is `lib/agentsCostNudge.ts`, tested beside it.
- **`readFirstGate.ts`** (PostToolUse, Read and Bash; PreToolUse, Edit/Write and the gworkspace Doc writes) records a full read of each row's docs and denies a call until every row that covers it has its docs recorded for the session. A full read is a Read that covers the whole file (no `offset` or `limit`, or bounds reaching its last line), or a Bash `cat` of it that no pipe trims (`BashReads.wholeFilePaths`): `isFullDocRead` and `isFullDocBashRead` in `lib/fullDocRead.ts`. Each row is its docs, its rules, its tools and the calls it covers; a test keeps the hook's PreToolUse matcher equal to the rows' tools. One refusal names every doc still missing and states each row's rules, and a row whose check throws fails open alone. The decision is `readFirstDecision` in `lib/readFirstGate.ts`, tested beside it. A path inside a workspace is matched relative to the workspace root (`rootRelative` in `lib/lintSet.ts`), so a row covers that workspace's files as it does the primary's, and a full read of any copy of a row's doc counts, the primary's or any workspace's. The rows:
  - `tiers` covers `lib/tiers/`, `tierGate.ts`, `gmailGate.ts` and `stepPermission.ts` at the primary root or in a workspace, and `.claude/settings*.json` at any root, and needs [the tier table](./targets-and-gates.md#which-tier-an-action-is-in).
  - `code-style` covers the code files ESLint lints (any `.ts`, `.js` or `.mjs` outside `dist/`, `coverage/` and `node_modules/`) minus each package's `generatedDir`, whose files are left to `generatedEditWarning.ts`, and needs `config/docs/code-style.md`. The set is `isLintedSource` in `lib/lintSet.ts`, shared with `formatAndLint.ts`.
  - `framework-style` covers the `code-style` row's files under `packages/framework/` and `packages/real-estate/`, at the primary root or in a workspace, and needs `packages/framework/docs/code-style.md`.
  - `prose-style` covers `.md` files outside the `personal` clone's `writing/` folder (the clone's path from `clonePathsOf`), `docs/agents/outcomes/` and the folders the lint set skips (`isUnignoredProjectFile` in `lib/lintSet.ts`), and needs `docs/prose-style.md`.
  - `writing` covers the gworkspace Doc writes in `gatedDocWrites` that put text in, and needs both `docs/writing-voice.md` and `docs/writing-craft.md`. **Text** is `create_doc` with `content`, `modify_doc_text` with `text`, any `find_and_replace_doc` or `insert_doc_elements`, and `batch_update_doc` when an operation inserts or replaces text. Formatting-only writes pass: `update_paragraph_style`, `modify_doc_text` with formatting arguments only, and `batch_update_doc` with style operations only. The refusal also names `docs/academic-writing-style.md` for academic work.
- **`formatAndLint.ts`** (PostToolUse, Edit/Write) runs Prettier (`--write --ignore-unknown`, reading only `.prettierignore` so the root's `packages/*` gitignore doesn't skip clone files) on every edited file, then `eslint --fix` on the edited file under the package's own `eslint.config.mjs` (`--flag v10_config_lookup_from_file`), with `@typescript-eslint/no-unused-vars` off for that run so an import added one edit before its use isn't flagged, then Prettier again if the fix changed the file. It adds each error left, as `line:col rule message`, as context, and says nothing for a clean file. It lints only files in the lint set (`lib/lintSet.ts`), and fails open on a crash, a timeout (20 s) or output it can't parse. A workspace file runs both tools from its workspace's root, with that root's own `node_modules/.bin/` binaries, so the branch's configs, ignore files and tool versions apply; the root is `rootOf` in `lib/lintSet.ts`. A missing binary skips its step, never falling back to the primary's. `npm run lint` stays the final gate. The feedback text is `lib/lintFeedback.ts`, tested beside it. A file written through Bash skips this hook and `readFirstGate.ts`; the git pre-commit hook (`.githooks/pre-commit`) then checks Prettier and ESLint on the staged files. The root's `prepare` (`scripts/lint/prepare.ts`, run by `npm install` and after each wrap-up) wires it as `core.hooksPath` in the root and each clone `clonePathsOf()` finds, so a commit in a package clone, primary or workspace, is checked too, from the root with the root's tools and `.prettierignore`.
- **`readCountNudge.ts`** (PostToolUse on Read/Grep/Glob/Bash; reset on UserPromptSubmit) counts reads per turn: Read, Grep, Glob, and Bash calls `bashReadGuard.ts`'s classifier calls reads. Edits, `tsc` and test runs are not counted. At 15 reads, and every 10 after, it reminds Claude to write findings down with `file:line`. Each subagent has its own count, and `repo-explorer` is exempt.
- **`contextNudge.ts`** (PostToolUse, every tool) is byro-repo's shim over the runner's context nudge (how a repo registers it: [`runner/src/contextNudge.ts`](../runner/src/contextNudge.ts)'s header), with the budget and handoff doc from `scripts/runner/runner.config.json`. It binds only ticket work: a runner step or a session whose claude holds an issue workspace's lease, so a session workspace or a plain root session runs unbudgeted; the leases are read only once the budget is passed (`lib/contextNudge.ts`, tested beside it). It resolves the runner as `@byronbroughten/spec-runner`, so a checkout needs `npm install` first; without it the hook exits with an error, which doesn't block the tool call.
- **`.claude/agents/repo-explorer.md`** is the project agent for sweeps; when to dispatch it is in [`docs/agents/delegation.md`](./agents/delegation.md).

## Switching Claude accounts

**Never suggest `/logout`**, which can revoke the stored refresh token; switch Claude accounts with `/login` or `cswap`.

## Seeing what a hook sees

To see what a hook sees, run `npm run session:probe -- <folder>`: it starts a one-turn headless session there with its own SessionStart hook added through `--settings`, and prints `$CLAUDE_PROJECT_DIR`, the hook's cwd and its input. For anything else a hook can see, extend `runner/src/SessionProbe.ts`.

## Per-session state

Per-session state lives in `$TMPDIR/claude-guardrails/`, keyed by session id: the branch record, the read log, the chore dry runs, the Drive owner cache, a marker for each doc the read-first rows record, and whether the AGENTS.md cost reminder and the context nudge fired. Supervision records and the facts file's session records live under `.runner/`, as their hooks' bullets say, and a workspace's lease is a `workspace.lease` file in its root worktree's git folder (`runner/src/IssueWorkspaces.ts`).
