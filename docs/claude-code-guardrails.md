# Claude Code guardrails

Mechanics of the Claude Code hooks and project agent. Why they are shaped this way: [`docs/agent-behavior-design.md`](./agent-behavior-design.md).

Fifteen Node hooks in `.claude/hooks/`: eight gate a call (the Bash-read guard, the tier gate, the gmail gate, the branch guard, the primary-edit guard, the STYLE gate, the prose gate and the doc content gate), five add feedback or a reminder, one records state for a gate, and one releases leases. All fail open except where noted. Session state lives in `$TMPDIR/claude-guardrails/`.

**Start every session at the primary root, or a workspace's root.** The settings, hooks and agent load only from a root's `.claude/`, so a session started inside `packages/*` runs with none of them. Each package's `CLAUDE.md` says so; restart at a root.

## The hooks and the project agent

`.claude/settings.json` registers fifteen Node hooks in `.claude/hooks/`, TypeScript that `node` runs by stripping types (erasable syntax only, `.ts` imports, nothing from `packages/`), fail-open (bad input allows the call) unless noted, plus one project agent. `bashReadGuard.ts`, `tierGate.ts`, `gmailGate.ts`, `branchGuard.ts`, `primaryEditGuard.ts`, `styleGate.ts`, `proseGate.ts` and `docContentGate.ts` gate a call; `branchRecord.ts` records what `branchGuard.ts` reads; `leaseRelease.ts` releases leases; `sessionIdContext.ts` records an interactive session in its issue's facts file; the others add feedback or a reminder.

- **`bashReadGuard.ts`** (PreToolUse, Bash) denies a Bash read of `columnConfigs.ts`, unless it is a grep or a `sed -n` range of at most 150 lines. It also denies a whole-file dump (`cat`, unbounded `head`/`tail`, `sed` without `-n`, `sed -n '1,$p'`) of a repo file over 150 lines. The deny message names the alternative. Piped input, small files, anything under a `.probe/`, `dist/`, `coverage/` or `node_modules/` folder at any depth, and anything outside the repo are not guarded. The `columnConfigs.ts` it guards is every package's, found through the `generatedDir` in each `sheets.config.json` (`lib/sheetsConfigs.ts`). `lib/bashReads.ts` is tested beside it. The classifier (`lib/bashReads.ts`) is shared with `readCountNudge.ts`.
- **`tierGate.ts`** (PreToolUse, Bash and the gworkspace write and create tools; PostToolUse, Bash) applies the tier gate. On Bash it allows the free reads, `git add` and the `git branch` changes [the tier list](./targets-and-gates.md#which-tier-an-action-is-in) names, a commit, `npm run wrap-up`, `app:build` and the deploy aliases, asks for a raw push, `npm publish` and a bare `clasp` or `sheets-framework`, and allows an `app:chore <name> -- --send` only after this session dry-ran that chore, which PostToolUse records. When the session's claude (the same ancestor walk as `leaseRelease.ts`) holds a live supervision record, every `gh` call but a known read asks, so the prompt shows the exact text the developer settled with the Supervisor: an issue or PR comment, edit or close, and a `gh api` call whose method isn't GET or HEAD (a field with no method is a POST, and `graphql` always is); `view`, `list`, `status`, `diff`, `checks`, `search`, `auth status` and `gh api` GETs pass, and so does every `gh` call from a session with no record. A `gh` inside another command's words, as in `bash -c` or `$(…)`, asks too. A Bash call is checked for a record only when its text names `gh`, and never in a runner step, which is never a supervisor; the runner config loads only for that check, and a check that throws counts as supervising. On gworkspace it allows creating, copying, importing and exporting a file, allows a Sheets or Docs write (or a non-sharing `update_drive_file`) on a file one of the developer's two Google accounts owns, and asks for one on anyone else's, naming the file and owner. The sharing tools, and an `update_drive_file` that changes sharing, always ask, naming who and at what permission. The owner comes from Drive's `owners` field, read with the gworkspace server's stored token for the agent account (`lib/driveOwners.ts`) and cached per session; a failed lookup asks. In a runner step, which `runner/src/ClaudeAgentStep.ts` marks with `BYRO_RUNNER_STEP`, every ask becomes a deny that says to record a `denied-tool` blocker; the step gets every free and tier-1 action the gate allows, and nothing else: other git verbs that change anything (`checkout`, `restore`, `reset`, `stash`, `rebase`, a `branch` delete or force), every `gh` call, reads included, since a step reads issues through `npm run issue:read` ([ADR 0007](./adr/0007-keep-untrusted-text-out-of-instructions-and-defer-containment.md)), and any command the gate doesn't classify, such as `node <script>`, `rm` or `mkdir`, stay denied. A gworkspace write is denied unless its file is among the ticket's targets, which `BYRO_STEP_TARGETS` carries ([ticket targets](./targets-and-gates.md#ticket-targets)). The one push it allows is `npm run wrap-up`'s, and wrap-up scans the lines each master adds over its remote for token shapes before pushing; a hit fails at `secret-scan`, naming file and line, and nothing is pushed ([`runner/README.md`](../runner/README.md)). The decisions are `lib/tiers.ts` and `lib/driveTiers.ts`, tested beside them.
- **`gmailGate.ts`** (PreToolUse, the four gmail filter, label and message-label tools) is the second half of an `/inbox` Sign-off. It allows a call when one `signed-off` Proposal in `~/.claude/inbox-data/proposals.md` covers it, and asks otherwise. A filter is covered when every criterion sits in the Proposal's query and every label it adds or removes sits in the action's `add` or `remove` clause. A bulk or unsubscribe change is covered the same way, and so is a new label whose name the `add` clause holds. A label named there that was created on apply counts by the id `changes.md` records for it. It denies adding `SPAM`, asks for any filter action other than adding and removing labels, and fails closed: unreadable data asks. Sending and drafting stay denied in settings. The decision is `lib/gmailGate.ts`, tested beside it.
- **`branchGuard.ts`** (PreToolUse, Bash) keeps a primary checkout (the root or a clone under `packages/`) on its branch. Its `mode` is strict: it denies every branch move (`git checkout <branch|sha>`, `checkout -b`, `switch`, `switch -c`) in a primary checkout. The interim form it replaced, still in `lib/branchGuard.ts`, left branch moves alone and denied only a `git commit` once HEAD's commit or branch changed since this session recorded it. File restores (`checkout -- <path>`, `checkout <ref> [--] <path>`, or a lone operand naming an existing path) always pass, `git -C` and `cd … &&` resolve the checkout acted on, and a target under `.claude/worktrees/`, where issue and session workspaces live beside Claude Code's own worktrees, is never denied. Subshells (`(cd x && …)`), `pushd`, `--git-dir` and `--work-tree` are not resolved: the guard catches accidents, not evasion. After its own HEAD-moving git command, a session's record is re-recorded before its next decision. Each deny names the way through: the issue workspace, or a fresh session once the other one is done. The decision is `lib/branchGuard.ts`, tested beside it; the I/O is `lib/branchRecords.ts`.
- **`primaryEditGuard.ts`** (PreToolUse, Edit/Write/NotebookEdit and Bash) keeps a session's edits and commits out of a primary checkout, where runs land. A file tool's path resolves through symlinks (a new file through its nearest existing folder) to the deepest primary checkout holding it, so a package clone is judged before the root that ignores `packages/*`. It is denied unless that checkout gitignores it: `.runner/`, `.probe/` and `node_modules` pass, as do `.claude/worktrees/`, which holds every issue and session workspace, and any path outside every checkout. On Bash it denies a `git commit` resolving to a primary checkout, resolving `git -C` and `cd … &&` as `branchGuard.ts` does. Bash writes such as `sed -i` and redirects are not caught: it catches accidents, not evasion. It is no tier gate, and a runner step meets it unchanged. The deny names `/start-issue <repo> <n>`, which moves the session into an issue workspace, then `npm run issue:start -- <repo> <n>` and `npm run issue:start -- --session <slug>`, and says to continue at the printed path. The decision is `lib/primaryEditGuard.ts`, tested beside it.
- **`branchRecord.ts`** (SessionStart, SessionEnd) records each primary checkout's branch and HEAD at the start of a session started at the primary root, keeping a live record across a compact, and marks it ended at the end, so a resumed session starts a fresh record. A record with no end, written under a day ago, is live.
- **`leaseRelease.ts`** (SessionEnd) releases every live workspace lease held by the session's claude process, the nearest `claude` ancestor of the hook (`scripts/runner/claudeAncestor.ts`, the same walk `npm run issue:start` uses to take one), so an interactive session's workspace is never released by hand. A `/clear` or `/resume` end keeps them, since the same process carries on. A session holding no lease changes nothing, and a runner step (`BYRO_RUNNER_STEP`) is skipped, since the run holds its lease under its own pid. It reads only the lease files, through the runner's `IssueWorkspaces.leases()` with byro-repo's config (`scripts/runner/runnerConfig.ts`), so no git runs at session end; a checkout needs `npm install` first. On the same real ends it also deletes the session's supervision record, the runner's `SupervisionRecords` file under `.runner/supervision/<pid>.json` naming the spec whose run this claude supervises and how many of its event lines it has explained, written by `npm run runner -- supervise <owner/repo> <n>` ([runner README](../runner/README.md)); a `/clear` or `/resume` end keeps it, so a cleared session carries on supervising. The decisions are `lib/leaseRelease.ts`, tested beside it.
- **`sessionIdContext.ts`** (SessionStart) puts `session: <id>` in context, for a handoff's `session:` line. When the session's claude (the same ancestor walk as `leaseRelease.ts`) holds an issue workspace's lease and `BYRO_RUNNER_STEP` is unset, it also adds `{agent: "implement", sessionId}` under that issue's `sessions` in `.runner/<repo>-<n>.facts.json`, through the runner's `FactsFile.addSession`, with the active `cswap` account and the config folder above the session's transcript, for wrap-up to read ([git-workflow](./agents/git-workflow.md)). A handoff's next session appends; a resumed or compacted session, keeping its id, isn't added twice; no lease, a session workspace's lease or a runner step adds nothing, and an unknown account or config folder skips the record. On a `clear` start whose cwd is inside an issue workspace leased to this claude, it adds one more line: the issue, that `/start-issue <repo> <n>` continues it from its handoff, and that work outside it needs `ExitWorktree` with `keep` first. A hook can't move the session's cwd, so that line is the whole mechanism. On a `clear` start whose claude holds a live supervision record (never a runner step's), it adds one line naming the run it supervises, that `/runner <owner/repo> <n>` on it carries on from the last explained event, and that `/runner` on another spec switches; with no record it adds nothing. The decisions are `lib/sessionRecord.ts`, tested beside it. A session that leases its workspace later, through `/start-issue`, is recorded by `npm run issue:start` instead, from `CLAUDE_CODE_SESSION_ID` and `CLAUDE_CONFIG_DIR` (falling back to `~/.claude`); its decision is `scripts/runner/startedSession.ts`.
- **`generatedEditWarning.ts`** (PreToolUse, Edit/Write) warns, without blocking, before an edit inside any package's `generatedDir`, naming that package's `*:gen:configs`: regenerate instead, floor entries included: fix the live tab or the seed ([`docs/generated-data.md`](../packages/framework/docs/generated-data.md)).
- **`agentsCostNudge.ts`** (PreToolUse, Edit/Write) reminds, without blocking, on the first edit to the root `AGENTS.md` in a session, once: every byte of that file loads on every turn, so add only what changes behavior on nearly every task ([`prose-style.md`](./prose-style.md#placement), [`prose-files.md`](./agents/prose-files.md#what-an-addition-to-agentsmd-costs)). Nested `AGENTS.md` files draw nothing. The decision is `lib/agentsCostNudge.ts`, tested beside it.
- **`styleGate.ts`** (PostToolUse, Read and Bash; PreToolUse, Edit/Write) records a Read of `config/docs/code-style.md` that covers the whole file (no `offset` or `limit`, or bounds reaching its last line), or a Bash `cat` of it that no pipe trims (`BashReads.wholeFilePaths`), and denies an edit to a code file ESLint lints (any `.ts`, `.js` or `.mjs` outside `dist/`, `coverage/`, `node_modules/` and `.claude/worktrees/`) until that read is recorded for the session. **The gate set is the lint set minus each package's `generatedDir`**, whose files are left to `generatedEditWarning.ts`; it is `isInLintSet` in `lib/lintSet.ts`, shared with `lintFeedback.ts`. The gate reads only the general doc; the framework's rules are reached by the router and `packages/framework/src/AGENTS.md`. The decision is `lib/styleGate.ts`; both are tested beside them. Cursor spells the read event `postToolUse`; the hook accepts that spelling too, so a Cursor session records the same marker. The framework style doc is a separate Cursor gate ([`docs/cursor-guardrails.md`](./cursor-guardrails.md)).
- **`proseGate.ts`** (PostToolUse, Read and Bash; PreToolUse, Edit/Write) records a full read of `docs/prose-style.md`, judged as `styleGate.ts` judges one, and denies an edit to a `.md` file until that read is recorded for the session. It skips `packages/writing/`, `docs/agents/outcomes/`, and the folders the lint set skips (`isUnignoredProjectFile` in `lib/lintSet.ts`). The decision is `lib/proseGate.ts`, tested beside it; the I/O both gates share is `lib/fullReadGate.ts`. Claude Code only; Cursor has no twin.
- **`docContentGate.ts`** (PostToolUse, Read; PreToolUse, the gworkspace Doc writes in `gatedDocWrites`, which a test keeps equal to the hook's matcher) records a full Read of `docs/writing-voice.md` and of `docs/writing-craft.md`, each judged as `styleGate.ts` judges one (`isFullDocRead` in `lib/fullDocRead.ts`, which every full-read gate shares), and denies a Doc write that puts text in until both reads are recorded for the session. **Text** is `create_doc` with `content`, `modify_doc_text` with `text`, any `find_and_replace_doc` or `insert_doc_elements`, and `batch_update_doc` when an operation inserts or replaces text. Formatting-only writes pass: `update_paragraph_style`, `modify_doc_text` with formatting arguments only, and `batch_update_doc` with style operations only. The deny reason names both sheets, and also `docs/academic-writing-style.md` for academic work. The decision is `lib/docContentGate.ts`, tested beside it. Claude Code only; Cursor has no twin.
- **`lintFeedback.ts`** (PostToolUse, Edit/Write) runs after the Prettier step, in the same settings entry so the order holds: `eslint --fix` on the edited file under the package's own `eslint.config.mjs` (`--flag v10_config_lookup_from_file`), with `@typescript-eslint/no-unused-vars` off for that run so an import added one edit before its use isn't flagged, then Prettier again if the fix changed the file. It adds each error left, as `line:col rule message`, as context, and says nothing for a clean file. It lints only files in the lint set (`lib/lintSet.ts`), and fails open on a crash, a timeout (20 s) or output it can't parse. `npm run lint` stays the final gate. The feedback text is `lib/lintFeedback.ts`, tested beside it. A file written through Bash skips this hook, the Prettier step, `styleGate.ts` and `proseGate.ts`; the git pre-commit hook (`.githooks/pre-commit`, wired by `npm install`) then checks Prettier and ESLint on the staged files.
- **`readCountNudge.ts`** (PostToolUse on Read/Grep/Glob/Bash; reset on UserPromptSubmit) counts reads per turn: Read, Grep, Glob, and Bash calls the classifier calls reads. Edits, `tsc` and test runs are not counted. At 15 reads, and every 10 after, it reminds Claude to write findings down with `file:line`. Each subagent has its own count, and `repo-explorer` is exempt.
- **`contextNudge.ts`** (PostToolUse, every tool) is byro-repo's shim over the runner's context nudge ([runner README](../runner/README.md#context-nudge)), with the budget and handoff doc from `scripts/runner/runner.config.json`. It binds only ticket work: a runner step or a session whose claude holds an issue workspace's lease, so a session workspace or a plain root session runs unbudgeted; the leases are read only once the budget is passed (`lib/contextNudge.ts`, tested beside it). It resolves the runner as `@byronbroughten/spec-runner`, so a checkout needs `npm install` first; without it the hook exits with an error, which doesn't block the tool call.
- **`.claude/agents/repo-explorer.md`** is a read-only (Read/Grep/Glob) Sonnet agent for sweeps of about 5+ files. It returns `file:line` plus verbatim quotes.

## Seeing what a hook sees

Never edit a hook to record what it sees; auto mode blocks it, and rightly. `npm run session:probe -- <folder>` starts a one-turn headless session there with its own SessionStart hook added through `--settings`, and prints `$CLAUDE_PROJECT_DIR`, the hook's cwd and its input. For anything else a hook can see, extend `runner/src/SessionProbe.ts`.

## Per-session state

Per-session state (the branch record, the read log, whether config/docs/code-style.md, docs/writing-voice.md and docs/writing-craft.md were read, whether the AGENTS.md cost reminder fired, and whether the context nudge fired) lives in `$TMPDIR/claude-guardrails/`, keyed by session id.
