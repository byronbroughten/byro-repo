# @byronbroughten/spec-runner

Runs a spec's tickets through implement, review, finding triage, fix, checks and wrap-up, one agent step at a time, and leaves the developer a review list. Its code imports nothing from the repo around it: everything repo-specific is injected config, so it can be split out later. Its words are in [`GLOSSARY.md`](./GLOSSARY.md).

A step whose ticket names targets also gets each target's tools (a spreadsheet's live `app:*` or `dev:*` aliases and the gworkspace Sheets tools, a Doc's gworkspace Docs tools), the gworkspace server's config, and the targets in its environment for the tier gate. |
| `@byronbroughten/spec-runner/FakeAgentStep` | The adapter run-loop tests script with `StepResult`s, or with functions of the request that act first, such as committing in its cwd. |

| `@byronbroughten/spec-runner/findingTriage` | Finding triage: `triagePrompt()` numbers the review's findings and asks for exactly one verdict per finding, Dismiss, Fix, Propose or Halt, stating each verdict's rules and editing nothing; `triageRecordSchema` and the `TriageRecord` type, and `triageOutputSchema`, which holds the records under `records`, with `triageRecordsOf()` to read them back; `triageRecordProblems()` refuses a record naming the verdict rule it broke, and a finding given zero or two verdicts; `haltScopeOf()` reads a Halt with no `haltScope` as scope `spec`. | `@byronbroughten/spec-runner/fixStep` | The fix step: `fixPrompt()` hands a fixer the Fix batch, each finding with its quote and rule, to fix in new commits, separate from the implement commit and followed by `npm run check`, or give up on (`judgement-call` or `checks-red`); `fixOutputSchema` and `fixOutcomesOf()`, one outcome per finding; `fixRecordProblems()` refuses outcomes that miss or repeat a finding, that disagree with whether the step committed, or that leave uncommitted changes; `giveUpRecordOf()` turns a give-up into a Halt scoped to the downstream tickets on the spec axis, else a Propose `decision`. |
| `@byronbroughten/spec-runner/gapCheck` | The gap check: `gapCheckPrompt()` asks, once every ticket of a spec is closed, for what the spec still asks that master doesn't do, skipping Phases marked `dropped` and stories an addendum drops; `gapCheckOutputSchema` and `gapCheckRecordOf()`, each gap with its drafted follow-up, which the runner never files. |
| `@byronbroughten/spec-runner/GhCli` | The real `gh` port: the run loop reads issues, sub-issues and open blockers and comments through it, and the wrap-up closes issues and reads parents and comments. |
| `@byronbroughten/spec-runner/implementStep` | The implement step: `implementPrompt()`, a non-interactive fork of the vendored `/implement` that works in the issue workspace, never asks, commits in each changed repo, runs `npm run check` and returns the implement record, carrying the latest handoff to a fresh step; `handoffCommentOf()` for the ticket comment the runner posts on a handoff, ending `session: <id>`; the handoff's optional `proposedSplit`, which the prompt says to fill when less than half the ticket is done; `handoffOnlyPrompt` for a step resumed past the live ceiling; `implementOutputSchema`, which holds the record under `record` because the API refuses a top-level union in a tool's input schema, `implementRecordOf()` to read it back, and the `ImplementRecord` type; and `implementRecordProblems()`, which refuses a record whose status disagrees with whether the step made a new commit (a handoff with a commit among them). A ticket that needed only GitHub writes (`gh issue edit` and `gh issue comment`, as the ticket describes them) returns `applied`, with no commit and a non-empty `githubWrites` list; only the ticket body and the developer's comments are instructions. The fork is recorded under `implement`'s `derivedInto` in byro-repo's `.claude/skills/upstream.json`. |
| `@byronbroughten/spec-runner/IssueWorkspaces` | The workspace module: `create()` takes an issue or a session key (`{ session: <slug> }`, every repo on `session-<slug>`) and builds an issue workspace (a root worktree outside the primary root with a worktree of each package clone inside, the issue's repo and any named extras on the issue branch, the rest detached at master), or returns the existing one; `promote()` puts a detached repo onto the issue branch partway through a ticket, `resume()` re-detaches the clean detached repos at the primary's current master and fails naming any with uncommitted changes or commits on no branch, `start()` resumes a key's workspace or creates it, refusing a live lease another holder has and taking one for the holder it's given; `takeLease()`, `releaseLease()` and `leaseOf()` manage a lease (a run's or session's pid and that process's start time in the root worktree's git folder, live while that same process runs, taken over once it dies), which `list()` reports too and `leases()` lists alone, reading only the lease files, `masterSet()` rebuilds a master set for the run loop's check of master after a ticket's red checks, and `list()` and `remove()` read and clear workspaces (`remove()` refuses the same unsaved work without force, and a live lease always). Clone paths, the workspace folder, the shared gitignored files, the installer and the title lookup are injected. byro-repo's values are in `scripts/runner/runnerConfig.ts`, behind `npm run issue:start -- (<repo> <n> | --session <slug>) [--claude]`, `npm run issue:list`, `npm run issue:promote -- <repo> <n> <repo-to-promote>` (the command the implement-step prompt names) and `npm run issue:remove -- (<repo> <n> | --session <slug>) [--force]`. |

| `@byronbroughten/spec-runner/Notices` | The notice port: one phone notification per run event, carrying only the spec title, a one-line summary and a link. |
| `@byronbroughten/spec-runner/NtfyNotices` | The plain ntfy adapter: posts the summary to a topic, with the spec title as its title and the link as its click target. The topic is a long random string from gitignored local config, byro-repo's in `scripts/runner/runner.local.json`. |
| `@byronbroughten/spec-runner/reviewStep` | The review step: `reviewPrompt()` runs the configured review skill on both axes against master and changes nothing; `reviewRecordSchema` and the `ReviewRecord` type, its findings as prose strings. |
| `@byronbroughten/spec-runner/reviewList` | The review list's formats: `ticketReviewListOf()` and `gapCheckListOf()` write the marked spec comments, `coveredLaterNotesOf()` the later ticket's note, and `undecidedCountOf()` counts unticked items for the end-of-run push. |
| `@byronbroughten/spec-runner/runKnobs` | Every knob a run reads, typed and defaulted in `defaultRunKnobs`: repo map, account, skill names, check and auth-check commands, allowed-tools lists, allowed write globs (`.claude/skills/**`, `.claude/agents/**` and `.claude/hooks/**`), turn caps for implement, review, triage, fix and the gap check, handoffs per ticket, ticket budget, live ceiling, triage pair, gap-check pair, review-list cadence (`end-of-run`, one push counting the undecided items, or `per-ticket`), idle poll interval and handoff doc. `loadRunKnobs()` lays a repo's JSON override file over them; `runKnobsOrDefaults()` falls back to the defaults when it can't, for a hook that fails open. byro-repo's override file is `scripts/runner/runner.config.json`. |
| `@byronbroughten/spec-runner/LandingLock` | The landing lock: a file per primary checkout holding pid, host and start time, taken over only when that pid is dead on this host, and polled while it is live. |
| `@byronbroughten/spec-runner/SessionProbe` | `SessionProbe`: starts a one-turn, no-tools headless session in a folder with a SessionStart hook added through `--settings`, and returns what that hook saw: `$CLAUDE_PROJECT_DIR`, its cwd and its stdin JSON. Nothing in the folder is edited. Behind `npm run session:probe -- <folder>`. |
| `@byronbroughten/spec-runner/SpecRun` | The run loop: `SpecRun.init(config).run(spec)` takes injected AgentStep, GitHub, notice and clock ports. It refuses a run whose open `ready-for-agent` tickets lack a valid Model fit or have a malformed `## Targets` line (a ticketless spec runs as its own ticket), Stops on a live ceiling at or below the ticket budget, a failed auth check, a missing primary clone or one off master, then runs the frontier ticket of the blocking graph, tie-broken by sub-issue order, through implement, review, finding triage when review found anything, the fix step when triage gave any Fix, checks and wrap-up in its issue workspace (an `applied` ticket goes straight from implement to wrap-up). An implement step that returns a handoff has its uncommitted work saved, untouched, to `backup/<branch>-handoff-<n>`, the handoff posted on the ticket ending `session: <id>`, and the ticket passed to a fresh implement step on the same pair, whose prompt holds only that latest handoff; run state keeps the handoff, so a rerun starts from it, and any snapshot before the next record, a crash's or a turn cap's, saves the work without resetting the tree. A handoff proposing a split raises a split Halt in place of the fresh step, offering `continue`, which launches the fresh step on the ticket's body as it then reads; a handoff past `handoffsPerTicket` (2), a backstop's included, is a Failure Halt saying to split the ticket first, whose `continue +1 handoff` allows one more. An implement step that crosses the live ceiling without handing off is killed and resumed for a handoff record only, which hands off as any other; any other record is a Failure Halt with the work snapshotted. Triage runs on the triage pair with no targets and gets one retry, resumed, for a refused record. The resumed implementer fixes the Fix batch while its peak context is under the ticket budget, else the resumed triage agent on the stronger pair does; a fixer that crosses the live ceiling is killed, its work reset away, and the batch handed to the triage agent. A give-up stays in run state as a Halt or Propose. Labels, pairs and targets are re-read before each launch. At wrap-up a ticket with Proposals gets one review-list comment on the spec (`<!-- review-list ticket=#n -->`, `R<n>.<k>` checkboxes, a collapsed Dismiss audit), and each `covered-later` Dismiss a note on its later ticket, each checked for its marker first so a rerun never posts twice; once every ticket is closed, the gap check runs in the primary root with no targets and its gaps become the last review list; a turn cap gets one fresh retry, then a Failure Halt on the spec issue, and a schema failure gets one at once, the run idling until it is answered. It never closes a split spec. When a ticket's checks go red it runs them in a master set, never in a primary checkout: a red master, or a master set that fails to build, Stops the run with the ticket left at its checks, and a green one leaves the red checks an `UnhandledStop`. Each outcome a later ticket will handle is an `UnhandledStop`: the ticket stays unlanded, the spec gets a comment and the run ends with one notice. With nothing runnable, an open Halt or another holder's lease leaves the run idle: one `Idle: nothing runnable.` push naming what's in the way, then a fresh pick every `idlePollMs`; any other wait ends the run, and when a ticket waits on the developer (`#n waits on you and blocks #x, #y`) the end-of-run push carries the rerun command. `requestStop(spec)` and a `stop spec` answer end the run after the current ticket, a halted ticket left committed and unlanded with its other Halts open; a push goes out on every Stop and end of run. `status(spec)` reads run state and GitHub and writes nothing: tickets landed, the current ticket and step, open Halts, waiting tickets, the account reading and any stop request. The per-spec run state, progress log (with how long preflight and each step took) and raw step logs live in the state folder, so a rerun resumes at the step reached. byro-repo's values are in `scripts/runner/runnerConfig.ts`, behind `npm run runner -- [status|stop] <owner/repo> <n>`. |
| `@byronbroughten/spec-runner/UnhandledStop` | The outcomes the run loop doesn't handle yet (red checks, a step error, a blocker, a schema failure, a wrap-up failure, a workspace that can't resume, a Model fit edited invalid, a Targets section edited malformed), and the error carrying one with its detail and log path. |
| `@byronbroughten/spec-runner/WrapUp` | The wrap-up script: `WrapUp.init(config).run(issue)` lands a ticket with no agent from its facts file. It builds and checks the merge commits in the issue workspace, records the outcome row, fast-forwards each primary's master under the landing lock, scans the lines each master adds over its remote for token shapes (a hit fails at `secret-scan`, naming repo, file and line, with the landing kept and nothing pushed) and pushes, deletes the branches, removes the workspace, closes the issue and checks the parent, merging the facts `transcriptFacts` computes over the passed ones, stopping at the first failure and recording finished steps so a rerun skips them. Facts with no branches but a `githubWrites` list (an `applied` ticket) skip the merges and checks; the outcome row is still committed on master and pushed, the workspace's issue branch is deleted, and the closing comment lists the writes. `runSession(slug, { holder })` lands a session workspace with no facts file: the repos whose `session-<slug>` branch is ahead of master, clones before root, fast-forwarding master where it can, with no checks, outcome row or GitHub calls. It refuses uncommitted changes in any repo and scans and pushes like an issue landing, then deletes the session branches, releases the lease and removes the workspace; `keepSession` instead leaves the workspace leased with every session branch level with master. Both refuse a workspace another live holder leases. Its progress file goes once it lands, so the same slug can land again. byro-repo's values are in `scripts/runner/runnerConfig.ts`, behind `npm run wrap-up -- <repo> <n>` and `npm run wrap-up -- --session <slug> [--keep]`. |
| `@byronbroughten/spec-runner/WrapUpFailure` | The typed failure a wrap-up stops on: conflict, red checks, dirty tree, foreign branch, failed parent check, network or secret scan. |
| `@byronbroughten/spec-runner/contextMeter` | `ContextMeter`: a session's peak context, the most input + cache-read + cache-creation tokens any one main-loop assistant message carried. Feed it stream-json events with `observe()` and read `peak`, or pass a whole transcript to `ContextMeter.ofTranscript()`. |
| `@byronbroughten/spec-runner/contextNudge` | The context nudge: `contextNudgeOf(transcript, options)` returns the handoff reminder once a transcript's peak context, read by the context meter, reaches the ticket budget (`ticketBudget`), else `undefined`. The reminder names the session's id for the handoff comment's closing `session: <id>` line, and the handoff doc when `handoffDocPath` is set. How a repo registers it is under [Context nudge](#context-nudge). |
| `@byronbroughten/spec-runner/limitGuard` | The limit guard: `readCswapList()` turns `cswap list --json` into per-account readings (a missing one is `undefined`, never thrown), and `decideStep()` picks launch, change account, Limit wait or Stop from them, the pinned account and the day's account changes, with `defaultLimitGuardKnobs` for its thresholds, margin and soft cap. |
| `@byronbroughten/spec-runner/outcomeLog` | The outcome log's file layout: a ticket's path under its spec's folder, its one-row table with `unrecorded` for facts nobody computed, and the commit message. |
| `@byronbroughten/spec-runner/transcriptFacts` | `transcriptFactsOf()`: the outcome facts computed from transcripts, found by the session ids and account config folder the runner records plus the handoff comments' `session: <id>` lines: pair, each implementer session's peak context, duration, API-equivalent cost (implementer, its subagents and any fixer) and triage cost, from the per-model price table `modelPrices`. `limitUsedOf()` writes Limit used from before and after readings. A fact with a missing transcript or reading stays `unrecorded`. |

## Context nudge

`contextNudge` decides and words the nudge; a repo registers a Claude Code hook that calls it, since Claude Code loads hooks only from the root's settings. The hook is a PostToolUse shim on every tool: it reads the hook input, skips subagents, reads the transcript at `transcript_path`, passes `contextNudgeOf()` the session's id and the `ticketBudget` and `handoffDocPath` knobs (through `runKnobsOrDefaults()` from the repo's override file), and writes any reminder as `additionalContext`. Firing once per session, deciding which sessions the budget binds and failing open are the shim's. byro-repo's shim is `.claude/hooks/contextNudge.ts`, registered in `.claude/settings.json`.

## Running under tmux

`npm run runner:tmux -- <owner/repo> <n>` starts the run in a detached tmux session, `runner-<repo>-<n>`, under `caffeinate -is` so the Mac stays awake; attach with `tmux attach -t runner-<repo>-<n>`. On a crash the wrapper sends a push (`scripts/runner/crashPush.ts`, to `runner.local.json`'s topic), since a crashed run sends none of its own, and the pane stays open with the error. Check on a run from any terminal with `npm run runner -- status <owner/repo> <n>`, and end it after its current ticket with `npm run runner -- stop <owner/repo> <n>`.

## Skills

The runner's interactive skills live in `skills/<name>/`: `/judge-findings <repo> #<spec>` walks a spec's undecided review-list items and closes the spec when none is left; `/mine-outcomes <repo> #<spec>` turns a landed spec's outcome rows into model-fit and process proposals, offers `/retro` on its outlier tickets and then clears the rows. byro-repo loads each one through a symlink in `.claude/skills/`, not a plugin ([layout](../docs/agents/upstream-skills.md#layout)). The skills link byro-repo's docs.

## Tests

Vitest, in the root's `tooling` project: `npm test` from the repo root, or `npx vitest run runner` for just these. `npm run tsc` and `npm run lint` from the root reach it too.
